## 2. 핵심 개념 — Task와 Block 분리

- **Task** (할 일): 해야 하는 것 자체. "무엇을?" → 투두 리스트/인박스/위젯
- **Block** (시간 블록): 타임라인 위 시작–끝 구간. "언제?" → 간트/오늘 뷰
- Task 1 : Block 0~N. Block 없는 Task = 미스케줄. Task 없는 Block = 순수 일정(수업/약속)
- **드래그드롭 정의**: 인박스 Task를 타임라인에 드롭 → Block 생성

Task 종류 3가지:
- `kind=day` 하루 투두 — 마감 없음, `day_of` 날짜 귀속, 암묵 마감 23:59
- `kind=deadline` 기한 투두 — `due_at` 필수, 간트 막대, 점수 계산 주 대상
- `kind=someday` 인박스 — 날짜 없음, 정렬 제외. **AI가 생성한 초안도 여기로 들어온다** (3.7)

> **v0.9 보강**: 매주 반복되는 고정 일정(수업·알바)은 Task도 Block도 아닌 **세 번째 것**이다. 3.8에서 `routines`로 따로 둔다. Block으로 저장하면 학기마다 수십 행이 생기고, Task로 두면 "완료"의 의미가 없다.

## 3. 기능 명세

### 3.1 간트/타임라인

- 줌 4단계: 일 / 주 / 월 / 분기. `pxPerMinute` 하나로 표현, `x = (t − t0) × pxPerMinute`
- 막대 2종: 계획 막대(Block, 실선) / 기간 막대(start_at~due_at, 고스트). 계획이 마감 밖 → 빨간 테두리
- today line, 주말 음영, 겹침 레인 분리

#### 3.1.1 실제로 만들어진 모양 (v0.9 정정)

v0.8까지 "가로 간트"였고, 주 뷰에서 하루 폭이 58px라 **2시간 Block이 4.8px**가 되는 문제를 "수정 후보"로 적어두었다. 프로토타입에서 그대로 재현됐고, 다음처럼 바꿨다.

| 줌 | 모양 | 편집 |
|---|---|---|
| 일 | 세로 열 1개 (72px/시간, 15분 스냅) | 이동·길이 조절·드롭 |
| 주 | **세로 열 7개 (월~일)** | 같음. **옆 열로 끌면 날짜가 바뀐다** |
| 월 | 달력 격자 + 마감 기간 막대 | 드롭 시 09:00 블록 |
| 분기 | 미니 달력 3장 | 보기 전용 |

세로로 세우면 주 뷰도 일 뷰와 같은 72px/시간 스케일을 쓰므로 **주 뷰가 읽기 전용이 될 이유가 사라진다.** 12장의 "가로 간트, 일뷰는 세로 전환"은 순서가 반대였다.

월·분기는 "언제 무엇이 걸려 있나"만 답하면 되므로 달력이 맞다. 다만 마감이 있는 일은 기간 막대로 이어 그리는데, 그대로 두면 한 달에 레인이 스물일곱 개까지 생겨 읽을 수 없는 벽이 된다. 그래서:

- 레인은 8개(작은 칸은 4개)까지만. 나머지는 `+n` 칩
- **같은 마감끼리 묶는다.** 마감이 다른 것만 나눈다
- 하루짜리는 막대로 그리지 않고 `+n` 칩으로 접는다
- 묶음의 제목은 **가장 급한 것 + "외 n개"**
- 칩을 누르면 아래로 펼쳐지는 팝업. 위치는 화면 밖으로 넘치지 않게 보정

### 3.2 드래그 앤 드롭

| 동작 | 결과 | 스냅 |
|---|---|---|
| 인박스 → 타임라인 | Block 생성 (길이는 `fit.ts`가 정한다, 아래) | 줌 눈금 |
| 막대 이동 | Block 시각 이동 | 15분/1시간/1일 |
| 막대 끝 드래그 | Block 길이 변경 | 동일 |
| 막대 → 인박스 | Block 삭제 (Task 유지) | — |
| 리스트 세로 드래그 | 수동 정렬 | — |

모바일: 롱프레스 220ms → 드래그, 햅틱. 웹: Alt로 스냅 해제.
**스냅 값은 저장하지 않는다** — DB엔 항상 정확한 타임스탬프.

> **블록 길이 ≠ 예상 소요시간** (`packages/core/src/fit.ts`). 6시간짜리 과제를 드롭했다고 6시간 블록을 만들면 안 된다. 잡을 길이는 `estimate_min − 이미 잡힌 블록 합`이고, 한 번에 최대 240분, 다음 일정에 막히면 거기까지다. 짧아졌으면 그 사실을 화면에 말해준다.

> **웹 구현 주의 — 드래그 중에는 DOM만 만진다.** 리렌더가 끼면 끊긴다. 대신 드래그가 끝나면 인라인 스타일을 **드래그 시작 값으로 되돌린다**. `''`로 지우면 React가 "바뀐 게 없다"고 판단해 다시 쓰지 않아 막대가 쪼그라든다. 그리고 3px 미만 이동은 드래그가 아니라 클릭이다 — 이 문턱이 없으면 클릭만 해도 시각이 ±7.5분 조용히 움직인다.

### 3.3 직접 추가 — 앱은 폼, 웹은 폼 + 한 줄

**앱 기본은 칸을 나눈 폼이다.** 한 줄 토큰 문법(`#학교 !5 6h @16:30`)은 데스크톱에서는 빠르지만, 폰에서는 `#` `!` `@` 를 치려고 키보드를 다섯 번 전환하게 되어 오히려 느리다.

**항상 보이는 필드 4개** — 제목 / 언제까지 / 얼마나 걸릴까 / 중요도
**세부 설정(접힘)** — 태그 · 시작일 · 지금 블록 잡기 · 반복 · 메모

폼 설계 원칙:
1. **필수는 제목 하나.** 나머지는 전부 기본값이 있다 (est 60분, importance 3)
2. **날짜·소요시간은 칩으로 탭 한 번.** 「직접」은 옆에 작게
3. **`kind`를 사용자가 고르지 않는다.** 입력에서 자동 결정: 날짜 없음 → `someday` / 날짜+종일 → `day` / 날짜+시각 → `deadline`
4. **저장 전에 등급·순위를 보여준다.** 중요도를 4→5로 바꾸면 미리보기가 즉시 바뀐다 — 이게 없으면 중요도는 전부 3으로 남고 점수 공식의 I 항(가중치 0.4)이 죽는다
5. **중요도는 접지 않는다.** 무엇을 접느냐는 곧 "이 값은 기본값으로 산다"는 선언이다

> **구현 주의**: 날짜 칩의 선택 상태는 **누른 칩의 이름**으로 기억한다. 해석된 날짜로 판단하면 금요일에 「내일」과 「이번 주말」이 같은 날이라 칩 두 개가 동시에 켜진다.

**한 줄 입력(웹 `N`)** 토큰:

| 토큰 | 매핑 | 예 |
|---|---|---|
| `#단어` | 태그 | `#학교` |
| `!1~!5` | importance | `!5` |
| `숫자h/m` | estimate_min | `2h` `90m` |
| 날짜·시각 | due_at | `내일 3시` `9/15` |
| `~` | start_at ~ due_at | `9/10~9/15` |
| `@시각` | Block 즉시 생성 | `@14:00` |

파싱 결과를 칩으로 미리보기 → 칩 클릭 수정. 실패분은 제목으로. **M5.**

### 3.4 태그

- `{name, color, sort_order}`, Task와 다대다
- 용도: 필터 / 막대 색(첫 태그) / 통계(태그별 주간 시간)
- **계층 없음.** 필요시 `학교/알고리즘` 이름 슬래시 + UI prefix 그룹핑
- 삭제는 툼스톤. 지운 태그가 할 일 줄에 남지 않게 조회에서 걸러낸다

### 3.5 위젯 (안드로이드)

| 위젯 | 크기 | 내용 | 상호작용 |
|---|---|---|---|
| 오늘 | 4×2 | 오늘 할 일 5개 + 완료 수 | 체크박스 탭 |
| 다음 일정 | 4×2 | 지금~6시간 Block | 탭 딥링크 |
| 급한 3개 | 2×2 | 점수 상위 3 + 등급색 | 탭 상세 |

갱신: 데이터 변경 시 push + WorkManager 15분 주기 + 자정 알람.
**위젯은 로컬 DB만 읽는다** (네트워크 의존 시 오프라인에서 빈 위젯).

> 앱 「오늘」탭의 상단 스트립을 **같은 6시간 창**으로 맞춰 두었다. 위젯과 앱이 다른 답을 내면 안 된다.

### 3.6 완료·진행률

- 완료 = `status=done` + `completed_at`, 삭제 안 함
- 하위작업은 같은 테이블 `parent_id`, 부모 `progress` **자동 계산** (구현 완료)
- 반복은 RRULE 저장, **완료 시점에 다음 인스턴스 생성** (미리 펼치지 않음). **M5**
- 뷰마다 진행률을 % 로 표시한다 — 오늘 몇 %, 이번 주 몇 %. 분모는 그 뷰에 속한 할 일

#### 3.6.1 뷰 여섯 (`core/views.ts`)

| 뷰 | 조건 |
|---|---|
| 오늘 | `day_of`가 오늘이거나 마감이 24시간 안 |
| 1주 | 마감이 **앞으로 7일** 안 |
| 월 | 마감이 **앞으로 30일** 안 |
| 전체 | 열린 것 전부 (급한 순) |
| 인박스 | `kind=someday` |
| 완료함 | `status=done` — **완료한 날짜별로 묶는다** |

> **「월」이 달력상 이번 달이 아닌 이유.** 「1주」가 "앞으로 7일"이라 결이 맞고, 달력 기준으로 잡으면
> 말일에 목록이 텅 비었다가 1일 아침에 갑자기 서른 개가 된다. 달력 화면(3.1)은 달 경계가 맞지만
> 이건 목록이라 아니다.

> **완료함을 날짜로 끊는 이유.** 하나의 긴 목록이면 어제 끝낸 것과 석 달 전 것이 같은 무게로 섞여
> 쌓일수록 못 쓰게 된다. 개수를 자르지는 않는다 — 화면이 보이는 것만 그리고, 옛것은 검색으로 찾는다.
> 라벨은 오늘 / 어제 / 9월 14일 (월)이고, `completed_at`이 없는 옛 데이터는 버리지 않고 맨 아래 「날짜 없음」으로 모은다.
> **로컬 날짜로 끊는다** — UTC로 자르면 밤 11시 50분에 끝낸 것이 어제 칸으로 밀린다 (7장).

검색(`matchesQuery`)은 제목·메모 부분 일치다. **지금 보고 있는 뷰 안에서만** 찾고, 결과가 0인데 다른 뷰에 있으면
「전체에서 찾기 (3개)」를 띄운다 — 뷰를 골라놓고 검색했는데 딴 게 나오면 혼란스럽고, 그렇다고 갇히면 안 된다.

### 3.7 AI 할 일 생성 (합류 예정)

팀원이 별도로 만들던 기능 — **목표를 입력하면 그에 맞는 할 일들을 생성**해준다. 시관에 통합한다.

**통합 방식은 미결.** 두 갈래이고 화면 설계가 갈린다:
- **A. 기능으로 흡수** — 추가 화면(3.3)에 "목표로 쪼개기" 진입점. 기존 화면을 거의 안 건드리고, 결과물은 인박스로 들어온다
- **B. 별도 진입점** — AI가 주인공인 탭/화면을 따로 둔다. 팀원이 만든 UI를 살리기 쉬우나 하단 탭 4개 구성(12장)이 바뀐다

#### 3.7.1 생성 결과는 인박스 초안으로 들어온다

**바로 목록에 넣지 않는다.** 한 번에 10건이 튀어나와 "급한 순"을 밀어내면 그날로 앱을 안 쓰게 된다.

```
목표 입력 → AI 호출 → 초안 N건 → 인박스(kind=someday) → 사용자가 하나씩 확정
```

- `kind=someday`라서 **정렬에서 자동으로 빠진다** (2장) — 별도 장치가 필요 없다
- 확정 = 사용자가 날짜/소요시간을 손보고 `day`나 `deadline`으로 승격시키는 행위
- 목표 자체를 **부모 Task**로 만들면 쪼개진 것들이 `parent_id`로 붙고 부모 `progress`가 자동 계산된다 (3.6) — **스키마 변경 없이 그대로 얹힌다**

#### 3.7.2 AI가 추정한 소요시간은 점수에 바로 넣지 않는다

점수 공식이 `slack = 남은 시간 − 남은 작업량`이므로 **estimate가 틀리면 정렬 전체가 틀린다.** AI가 "논문 읽기 2h"를 지어내면 그 숫자가 그대로 등급이 된다.

- `estimate_is_ai` 플래그로 추정치임을 표시 (점선 테두리 등)
- **사용자가 확정하기 전에는 점수 정렬에 넣지 않는다**

#### 3.7.3 오프라인 우선의 유일한 예외

7장은 "로컬 DB가 진실의 원본, 앱은 네트워크 없이 완전 동작"이 원칙인데 AI 호출만은 네트워크가 필수다. 숨기지 말고 **이 기능만 온라인 전용**임을 UI에 명시한다.

#### 3.7.4 비용과 키 — 여기서 돈이 샌다

- **API 키를 앱에 넣으면 안 된다.** APK는 뜯으면 문자열이 보인다(A.5). 호출은 Supabase Edge Function 경유, 키는 Function Secret
- **계정당 호출 상한**을 처음부터 건다
- 같은 목표로 반복 호출되는 경우가 많으므로 **응답 캐싱** 고려

#### 3.7.5 합치기 전 확인할 것

1. 팀원 구현이 **어떤 입출력**인가
2. 호출이 **클라이언트에서 직접**인가 서버 경유인가
3. 데이터 모델이 시관 `tasks`와 어떻게 매핑되는가
4. 16장 모듈 배정 — 6번째 모듈로 둘 것인가

### 3.8 고정 일정 · 수면 · 자동 배치 (v0.9 신설)

할 일은 쌓이는데 "언제 할지"는 사람이 매번 정해야 한다. 빈 자리를 찾는 일은 규칙이 분명해서 기계가 낫다. **단 기계가 정한 것을 말없이 저장하지는 않는다** (3.8.3).

규칙은 전부 `packages/core/src/schedule.ts`에 있고 웹·앱·위젯이 같은 함수를 부른다. 15장의 "자동 스케줄링(점수 함수 + 그리디)" 후보가 여기로 승격됐다.

#### 3.8.1 막혀 있는 시간을 먼저 받는다

**수면** — 평일·주말 두 벌만 받는다. 요일별 7줄은 정확하지만 아무도 안 채운다.
자정 기준 분으로 저장하고, `start > end`면 자정을 넘긴 것이다(01:00 취침 = 60, 08:00 기상 = 480).
**어느 규칙을 쓸지는 「기상하는 날」의 요일로 정한다** — "주말엔 늦게 잔다"는 금요일 밤을 말하는 것이기 때문이다.

**시간표 (`timetables`)** — 고정 일정 한 벌. 학기일 수도, 알바 스케줄이 바뀐 시기일 수도 있다.

> **기간을 고정 일정마다 두지 않는다.** 개강이 한 주 밀리면 수업 여섯 개를 전부 고쳐야 한다.
> 한 벌로 묶으면 한 줄이다. 그리고 이름이 있어야 전환과 복제가 말이 된다.

- **기간이 겹치지 않는다.** 새 시간표를 만들면 이전 것을 그 전날로 닫는다 — 겹쳐 두면 자동 배치가 두 벌을 합쳐서 피해버린다
- 시간표가 하나도 없으면 「기본」 한 벌을 만들어 둔다. "먼저 시간표를 만드세요"가 첫 화면이 되면 안 된다
- **복제해 새로 만들기**가 빈 것보다 앞에 온다. 다음 시간표는 대개 지금 것에서 몇 개만 바뀐다
- 화면 문구에 「학기」를 쓰지 않는다. 학생만 쓰는 앱이 아니다

**고정 일정 (`routines`)** — 수업·알바·운동처럼 매주 같은 자리에 있는 것. 어느 시간표에 속하는지(`timetable_id`)를 갖는다.

> **Block으로 저장하지 않는다.** 한 학기 15주 × 주 3회면 45행이고, 강의 시간이 한 칸 바뀌면 그 45행을 전부 고쳐야 한다. 규칙으로 두고 화면·계산에서 그때그때 펼친다 — 펼친 것은 저장되지 않는 **가상 Block**이고 id가 `v:`로 시작해 진짜와 구분된다.

- 요일은 배열(0=월 … 6=일). "월·수 10:30–12:00"이 **한 행**이다
- 기간은 갖지 않는다. 그 일정이 언제 유효한지는 **속한 시간표**가 정한다
- **자정을 넘는 일정은 지원하지 않는다.** 펼칠 때 길이가 음수가 된다. 둘로 나눠 넣게 한다
- **겹치는 고정 일정은 만들 수 없다.** 자동 배치 입장에서는 합쳐진 한 덩어리라 구분할 이유가 없고, 겹쳤다는 건 대개 실수다

**입력 방식은 플랫폼마다 다르다.**

| | 입력 | 이유 |
|---|---|---|
| 웹 | **시간표 격자에 직접 드래그** (에브리타임식) | 마우스로는 끌어서 시간을 잡는 게 가장 빠르다 |
| 앱 | **`+ 추가` 시트(폼)** — 입력하는 동안 **격자에 들어갈 자리를 미리 보여준다** | 폰에서 작은 격자를 손가락으로 끌어 15분을 맞추는 건 답답하고, 타임라인의 롱프레스 드래그와 제스처가 겹친다 |

양쪽 공통: 격자는 **고른 시간표 한 벌만** 그린다 — 전부 겹쳐 그리면 지난 시간표가 같이 보인다(v0.9에서 실제로 그랬다). 월~금 기본이고 **주말 일정이 생기면 토·일 열이 붙는다.** 표시 시간 범위는 등록된 일정에 맞춰 자동으로 넓어진다(기본 08:00~22:00). **수면은 빗금 띠로 같이 깔린다** — 이 격자의 목적이 "자동 배치가 어디를 피하는가"를 보여주는 것이라 수면도 같이 보여야 말이 된다.

#### 3.8.2 자동 배치 규칙

세 층으로 나눈다. 섞으면 테스트가 불가능해진다.

| 층 | 함수 | 답하는 질문 |
|---|---|---|
| 1 | `expandRoutines` / `sleepSpans` | 무엇이 막혀 있나 → 가상 Block |
| 2 | `freeSpans` → `insetSpans` | 어디가 비었나 → 구간 목록 |
| 3 | `autoSchedule` | 무엇을 넣나 → 제안 목록 |

규칙:

- **넣을 양 = `estimate_min` − 이미 잡힌 Block 합** (`fit.ts remainingToSchedule`). 블록 길이는 예상 소요시간이 아니다 (3.2)
- **한 번에 최대 240분**, 최소 15분. 넘으면 여러 날로 쪼갠다
- **마감을 넘겨 잡지 않는다.** 금요일 23:59 마감이면 토요일에 배치하지 않는다
- **`someday`는 제외한다.** 마감 없는 것을 시간표에 밀어 넣으면 정작 급한 게 밀린다 (3.7.1과 같은 이유)
- 15분 격자에 맞춘다. 저장은 정확한 값 (3.2)
- 우선순위는 4장 점수 내림차순 **그리디**
- **맞닿는 자리마다 간격** (`settings.gap_min`, 기본 10분) — 빈 구간의 **양 끝을 깎는다.** 수업이 12:00에 끝나자마자 12:00에 다음 일을 시작할 수는 없다. 이동하고 정리하고 화장실도 간다. 붙여서 잡아두면 지키지 못하고 그때부터 시간표 전체가 밀린다.
  단 **범위의 처음(=지금)과 끝은 깎지 않는다.** 그건 무언가에 맞닿은 게 아니라 경계다 — 지금이 14:00인데 14:10부터 시작하라고 할 이유가 없다

**범위는 둘.**

| | 끝 | 근거 |
|---|---|---|
| 7일 | 지금부터 이레 | 더 넓히면 "다다음 주 화요일 오전"처럼 지켜지지 않을 약속이 쌓이고, 그러면 제안 전체를 안 믿게 된다 |
| 오늘 | 지금부터 **내일 기상 시각** (`endOfWakingDay`) | 자정으로 끊으면 새벽 1시에 자는 사람은 00:00~01:00을 통째로 버린다. 기상 시각까지로 잡으면 수면 띠가 01:00~08:00을 알아서 막으므로 실질적으로 "지금부터 잘 때까지"가 된다 |

#### 3.8.3 결과는 제안이지 저장이 아니다

```
제안 → 검토(고치기) → 적용
```

- 타임라인에 **점선 막대**로 뜬다. 진짜 Block과 같은 레인 계산을 타고 **끌어 옮기고 길이를 바꾸고 목록으로 던져 버릴 수 있다**
- **「적용」을 눌러야** Block으로 저장된다. 그전까지 DB는 그대로다
- 구현상 제안은 id에 `p:` 접두사를 붙인 Block 모양으로 감싼다 — 저장 지점 한 곳에서만 갈라내므로 "제안인데 실수로 저장됐다"가 구조적으로 생기지 않는다

**검토 패널의 무게중심은 제안 목록이 아니라 「안 들어간 것」이다.** 부족한 시간과 이유(`빈 자리가 없다` / `마감이 지났다` / `일부만 들어감`)를 같이 보여주고, 무엇을 해야 하는지까지 적는다 — 마감을 미루거나, 예상 시간을 줄이거나, 다른 일을 빼야 한다.

> 자동 배치의 쓸모는 시간을 채워주는 데 있지 않고 **"이번 주엔 다 못 한다"를 월요일에 알려주는 데** 있다. 금요일에 알면 늦다.

#### 3.8.4 고정 일정 체크

타임라인의 고정 일정 띠에 체크박스를 단다. 날짜별로 기록한다(운동·수업 출석 등).

- **점수에 넣지 않는다.** 고정 일정은 Task가 아니므로 급한 순 정렬·등급·뷰 진행률(3.6)에 끼지 않는다. **수업 출석이 과제 우선순위를 밀어내면 안 된다.** 대신 타임라인 머리에 `고정 2/3`으로 따로 센다
- **분모는 이미 지나간 것만.** 월요일 아침에 이번 주를 보며 `0/12`를 보는 건 틀린 정보다. 미래 일정은 체크할 수 없다
- **지난 날짜는 체크할 수 있다.** 어제 운동을 깜빡 체크 안 했으면 돌아가서 찍을 수 있어야 한다
- **일정을 지워도 체크 기록은 남는다.** 학기가 끝나 수업을 지웠다고 지난 석 달의 출석이 사라지면 안 된다

## 4. 우선순위 점수 (확정)

핵심: 남은 시간이 아니라 **여유(slack)**를 쓴다. 사흘 남았지만 20시간 걸리는 일 > 내일 마감 10분 일.

```
slack = (due_at − now) − (estimate_min − spent_min)        // 시간 단위
U     = 100 / (1 + max(slack, 0) / 48)                     // 마감 임박도 0~100
I     = (importance − 1) × 25                              // 1~5 → 0~100
score = 0.6 × U + 0.4 × I + boosts
```

- 반감 상수 48h: "며칠 앞부터 급해 보이는가". 설정에서 24~96h
- 가중치 0.6/0.4: 급함↔중요 슬라이더 하나로 조절
- U 곡선: slack 0→100, 12h→80, 24h→66.7, 48h→50, 1주→22, 2주→12.5

**Boosts**: 마감 지남 +30 · `kind=day` +10 · `spent_min>0` +5 · pinned +∞ · 선행 미완료 −20(v2) · someday 제외

**등급**: 90+ 지금당장 / 70–89 오늘안에 / 40–69 이번주 / <40 여유
→ 리스트 좌측 스트라이프, 간트 테두리, 위젯 점 색. 숫자 점수는 기본 숨김.

**검산** (기준 2026-09-02 14:00):

| 할 일 | 마감 | 예상 | 중요도 | slack | U | I | 점수 | 등급 |
|---|---|---|---|---|---|---|---|---|
| 학회비 납부 | 08-31(지남) | 0.2h | 3 | − | 100 | 50 | 110 | 지금당장 |
| SINE 발표자료 | 09-03 09:00 | 4h | 4 | 15h | 76.2 | 75 | 75.7 | 오늘안에 |
| 설거지(하루) | 오늘 23:59 | 0.5h | 2 | 9.5h | 83.5 | 25 | 70.1 | 오늘안에 |
| 운영체제 과제 | 09-04 23:59 | 6h | 5 | 52h | 48.0 | 100 | 68.8 | 이번주 |
| 포폴 리뉴얼 | **10-15 14:00** | 20h | 3 | 1012h | 4.5 | 50 | 22.7 | 여유 |

> 이 다섯 줄은 `packages/core`의 실제 함수로 재현되며 소수 첫째 자리까지 일치한다. **첫 테스트 파일이 이 표 그대로다.** (v0.9: 마지막 줄 마감이 `10-15`로만 적혀 있었는데 slack 1012h가 나오려면 `14:00`이어야 한다 — 표를 정정.)

**검토 필요**: 설거지(70.1)가 운영체제 과제(68.8)보다 위다. 30분짜리 집안일이 6시간짜리 과제를 이기는 것이 납득되는가 — `kind=day` +10 부스트가 만든 순서이며, 이상하면 부스트 값이 조정 대상.

**점수 함수는 `packages/core`에 두고 웹·앱·위젯이 공유한다.** 세 곳 각각 구현하면 정렬이 어긋난다.

## 5. 데이터 모델 (PostgreSQL, 로컬 SQLite·Dexie 동일 구성)

**tasks**: `id`(uuid, 클라이언트 생성 UUIDv7) · `user_id` · `title` · `notes` · `kind`(day/deadline/someday) · `status`(todo/doing/done) · `day_of`(date) · `start_at` · `due_at` · `estimate_min`(기본 60) · `spent_min` · `importance`(1–5, 기본 3) · `progress` · `pinned` · `parent_id` · `rrule` · `sort_order`(double, 중간값 삽입) · `score`(캐시) · `source`(manual/quickadd/ai/import) · `estimate_is_ai` bool · `is_locked` bool + `enc_blob` bytea (v2 잠금항목 예약, A.2) · `created_at`/`updated_at`/`completed_at` · `deleted_at`(툼스톤) · `rev`(bigint)

**blocks**: `id` · `user_id` · `task_id`(NULL 허용) · `title`(task_id NULL일 때) · `start_at`/`end_at`(CHECK end>start) · `is_all_day` · `source`(manual/drag/timer/import) · `deleted_at` · `rev`

**tags**: `id` · `user_id` · `name` · `color` · `sort_order` · `deleted_at` · `rev` · UNIQUE(user_id, name)
**task_tags**: (task_id, tag_id) 복합 PK

| `deleted_at` / `rev` | | 툼스톤 · 동기화 |

> **기간이 겹치지 않는 것이 규칙이다.** 코드가 강제하지는 않고(겹쳐 들어오면 전부 적용한다),
> 새로 만들 때 이전 것을 닫아서 지킨다. 겹치면 자동 배치가 두 벌의 일정을 합쳐서 피한다.

**routines** — 매주 반복되는 고정 일정. 규칙으로 저장하고 펼치지 않는다 (3.8.1)

| 컬럼 | 형 | 비고 |
|---|---|---|
| `id` | uuid | 클라이언트 생성 |
| `user_id` | uuid | |
| `timetable_id` | uuid | 어느 시간표에 속하는가 → `timetables.id` |
| `name` | text | 수업·알바·운동 이름 |
| `weekdays` | int[] | **0=월 … 6=일**. `Date.getDay()`(0=일)와 다르므로 변환한다 |
| `start_min` / `end_min` | int | 자정 기준 분. `end > start` (자정 넘김 미지원) |
| `color` | text | `#rrggbb` |
| `deleted_at` / `rev` | | 툼스톤 · 동기화 |

**settings** — 사용자당 한 행

| 컬럼 | 형 | 비고 |
|---|---|---|
| `user_id` | uuid | **PK** |
| `sleep` | jsonb | `{weekdayStart, weekdayEnd, weekendStart, weekendEnd}` 전부 자정 기준 분 |

| `updated_at` / `rev` | | |

**routine_checks** — 그 날 그 일정을 했는가 (3.8.4)

| 컬럼 | 형 | 비고 |
|---|---|---|
| `id` | text | **`${routine_id}:${day}`로 계산한다** ← 아래 |
| `user_id` | uuid | |
| `routine_id` | uuid | 일정이 지워져도 기록은 남는다 (FK를 걸지 않거나 ON DELETE SET NULL) |
| `day` | date | **로컬 날짜** (7장) |
| `checked_at` | timestamptz | |
| `deleted_at` / `rev` | | 체크 해제 = 툼스톤 |

> **`id`를 계산해서 만드는 것이 이 테이블의 핵심이다.** 랜덤 UUID였다면 폰에서 한 번, 웹에서 한 번 체크했을 때 같은 날 체크가 두 줄 생긴다. 규칙으로 만들면 **같은 행을 두 번 쓰는 것**이라 7장의 LWW가 그대로 먹고 병합이 필요 없다.
> 이것이 **7장 원칙(클라이언트 UUIDv7)의 유일한 예외**다. 예외를 둔 이유는 이 행이 "새로 만드는 것"이 아니라 **(일정, 날짜) 한 쌍에 대한 사실**이기 때문이다.

인덱스:
```sql
CREATE INDEX idx_tasks_active_score ON tasks (user_id, score DESC)
  WHERE deleted_at IS NULL AND status <> 'done';
CREATE INDEX idx_blocks_range ON blocks (user_id, start_at, end_at)
  WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_rev ON tasks (user_id, rev);
CREATE INDEX idx_routine_checks_day ON routine_checks (user_id, day)
  WHERE deleted_at IS NULL;
CREATE INDEX idx_routines_timetable ON routines (user_id, timetable_id)
  WHERE deleted_at IS NULL;
```
그 외: `users`, `devices`(푸시 토큰), v2용 `task_deps(before_id, after_id, type)`
AI 기능 도입 시: `ai_generations(id, user_id, goal_text, created_at, token_cost)` (3.7.4)

## 6. API (REST + JWT 15분 / 리프레시 30일 회전)

`POST /auth/{register,login,refresh}` · `GET|POST /tasks` · `PATCH|DELETE /tasks/{id}` (If-Match: rev) · `GET|POST|PATCH|DELETE /blocks` (GET는 from/to 필수, PATCH 200ms 디바운스) · `/tags` · **`/routines`** · **`/settings`** · **`GET|POST /routine-checks`** (GET는 from/to 로컬 날짜) · **`GET /today`** (위젯 전용 집계) · `GET /sync?since={rev}` · `POST /sync` · `GET /stats`(v2) · **`POST /ai/breakdown`** (3.7.4)

> 자동 배치에는 엔드포인트가 없다. **전부 클라이언트에서 계산한다** — 입력(할 일·블록·고정 일정·수면)이 이미 로컬에 다 있고, 서버를 태우면 오프라인에서 못 쓰게 된다 (7장).

## 7. 동기화 — 오프라인 우선

로컬 DB가 진실의 원본, 서버는 허브. 앱은 네트워크 없이 완전 동작. **예외는 AI 생성 하나뿐이다** (3.7.3).

1. **ID 클라이언트 생성** (UUIDv7) — 오프라인 생성·멱등 요청. **예외: `routine_checks.id`는 계산값** (5.1)
2. **아웃박스 큐** — 로컬 쓰기 + outbox 로그 → 온라인 시 순서대로 flush
3. **rev 커서** — 사용자별 단조증가, `GET /sync?since=`로 증분
4. **툼스톤** — `deleted_at`, 90일 후 서버 정리
5. **충돌 = 레코드 LWW** (기준: 클라이언트 `updated_at`), 예외 2개:
   - `status`는 `done`이 이긴다
   - `spent_min`은 큰 값이 이긴다

주기: 포그라운드 진입 / 변경 후 2초 디바운스 / 15분 백그라운드. 웹은 온라인 우선 + 낙관적 업데이트. 실시간 푸시는 v2.

**시간대**: 모두 UTC `timestamptz`, 표시할 때만 변환. 단 `day_of`·`routine_checks.day`·`routines.active_*`·반복 규칙은 **로컬 날짜** (UTC 저장 시 자정 근처에서 오늘 할 일이 어제로 밀림). users에 타임존(Asia/Seoul) 저장.

> **구현 주의**: 좌표·눈금 계산에서 `ms % 86400000`으로 자정을 구하면 안 된다. 그건 UTC 자정이라 KST에서는 09:00이다 — 주 뷰 눈금이 전부 "9시"로 찍히는 버그가 실제로 났다. 로컬 `Date` 접근자로 걸어야 한다.

|---|---|---|

**확정 근거**
- 소셜 로그인 + 계정 연결 + 계정 삭제가 들어오며 자체 구축 M2가 2~3주 → **4~5주**가 된다. 늘어난 4~5주는 전부 남이 이미 푼 문제다
- 카카오가 공식 제공자에 포함 — 국내 사용자를 받을 앱에서 실질적 차이
- **AI 호출 프록시**가 Edge Function 하나로 끝난다 (키 은닉 + 레이트 리밋)
- **학습은 RLS 정책 설계로 챙긴다.** 정책을 잘못 쓰면 남의 데이터가 그대로 샌다 — 스스로 공격해보는 게 IDOR/권한상승 실습 그 자체다 (A.10)

**결정을 미룰 수 있게 해둔 장치 — Repository 인터페이스** (이미 구현됨, `packages/core/src/repo.ts`):
```ts
interface TaskRepo { list(f); get(id); upsert(t); upsertMany(ts); remove(id); syncSince(rev); }
interface BlockRepo { … }  interface TagRepo { … }
interface RoutineRepo { … }  interface RoutineCheckRepo { … }  interface SettingsRepo { … }

class LocalTaskRepo    implements TaskRepo {}  // M1 웹(Dexie) · M3 앱(SQLite)
class SupabaseTaskRepo implements TaskRepo {}  // M2
```
스키마를 PostgreSQL로 잡아두었으므로 이관은 pg_dump + Auth 매핑 수준. **되돌릴 수 없는 결정이 아니다.**

### 9.2 계정 연결 (identity linking)
`users : identities = 1 : N`으로 처음부터 분리.

```sql
CREATE TABLE identities (
  id uuid PRIMARY KEY,
  user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  provider text NOT NULL,       -- google | kakao | apple | email
  provider_uid text NOT NULL,   -- 제공자 안정적 subject ID (이메일 아님)
  email text,
  email_verified bool NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now(),
  last_used_at timestamptz,
  UNIQUE (provider, provider_uid)
);
```
- **자동 연결**: 이메일이 같고 **양쪽 다 검증된 이메일**일 때만
- **수동 연결**: 로그인 상태에서 설정 → 계정 → "구글 계정 연결"
- **연결 해제**: identity 2개 이상일 때만

**보안 주의 — 이 앱에서 가장 위험한 코드:**
1. **미검증 이메일 자동연결 = 계정 탈취.** `email_verified=true`일 때만 자동연결
2. **카카오는 이메일이 선택 동의** — 없거나 미인증으로 올 수 있음 → 자동연결 제외, 수동만
3. **식별자는 `sub`**. `provider_uid`에 이메일 넣으면 제공자 쪽 이메일 변경 시 계정 분리
4. **PKCE + state + nonce 필수**

## 10. 보안 — 하는 것 여덟 줄

실제 사고는 암호화가 아니라 **권한 검사**에서 난다. 아래 여덟 줄이 전부이고 합쳐서 **3~4일**이다. 위협 모델·E2EE 비교·RLS 정책 SQL·자가 점검 절차는 **부록 A**로 옮겼다. **팀원 넷은 부록을 읽지 않아도 된다** (10.1).

| # | 하는 것 | 왜 | 시점 | 담당 | 비용 |
|---|---|---|---|---|---|
| 1 | TLS 1.3 + HSTS, HTTP→HTTPS 301 | 같은 와이파이에서 가로채기 | M2 | ③ | ~0 |
| 2 | 저장 시 암호화 켜기 (Supabase 기본) | 설정 한 줄 | M2 | ③ | ~0 |
| 3 | **RLS 정책 전 테이블 + 자가 점검 1~3번** | **안 켜면 아무나 남의 데이터를 읽는다** | M2 | ③ | 2~3일 |
| 4 | **AI 키 서버 경유 + 계정당 호출 상한** | 보안이 아니라 돈 | M4.5 | ③ | ~반나절 |
| 5 | 토큰은 `expo-secure-store`(Keystore) | `AsyncStorage`는 평문 | M3 | ③ | ~반나절 |
| 6 | 비밀 분리 + `gitleaks` pre-commit | 푸시된 키는 회전 말고 복구 방법이 없다 | M0 | ③ | ~반나절 |
| 7 | 메모 렌더링 전 DOMPurify + 웹 CSP | 메모가 마크다운이라 XSS 표면이 생긴다 | M1 | ⑤ | ~1일 |
| 8 | 계정 삭제 경로 + 처리방침 게시 | **Play 심사 통과 조건** (9.4 · 13.3) | M0·M2 | ③ | ~반나절 |

**3·4·8번은 뺄 수 없다.** 각각 **Supabase를 쓰는 조건 / 크레딧이 마르지 않는 조건 / 스토어에 올라가는 조건**이기 때문이다.

> **RLS 대상 테이블에 v0.9의 셋을 빠뜨리지 말 것** — `timetables` · `routines` · `routine_checks` · `settings`. 조인·부속 테이블을 빠뜨리는 것이 A.4의 실수 2번이다.

### 10.1 팀원 넷은 이걸 몰라도 된다

RLS를 각자 이해해야 하는 구조면 다섯 명이 다섯 번 실수한다. **레포지토리 계층에서 `user_id`를 강제 주입**하고, 나머지는 그냥 `taskRepo.list()`만 부른다.

```ts
// packages/core — 여기 한 곳만 맞으면 된다
class SupabaseTaskRepo implements TaskRepo {
  list(f) { return db.from('tasks').select().eq('user_id', this.me) /* … */ }
}
```

- 화면 코드에 `user_id` 조건을 직접 쓰는 PR은 리뷰에서 막는다 — `CODEOWNERS`로 `packages/core`를 ②③이 소유 (16.9)
- 실력 편차를 다루는 방법은 조심시키는 게 아니라 **틀릴 수 없게 만드는 것**이다 (16.7)

### 10.2 안 하기로 한 것 — 이유까지

| 항목 | 왜 안 하나 |
|---|---|
| 전체 E2EE | AI 생성(3.7)과 양립 불가. 검색·위젯·알림·계정복구도 함께 깨진다 |
| 로컬 DB SQLCipher | 위젯은 앱 프로세스가 아니라 키를 못 꺼낸다. 켜면 위젯이 죽는다 (3.5) |
| 인증서 핀닝 | 갱신 사고로 앱이 통째로 죽는 위험이 이득보다 크다 |
| **Sentry + 로그 스크러빙** | **범위 축소로 제외.** 크래시·ANR은 Play Console **Android vitals**로 본다 |
| **자가 점검 4~11번** | **여유 있으면.** 1~3번(IDOR·RLS 우회)만 M2 종료일에 필수 |

**암호화 범위는 A+B(전송 구간 + 저장 시)로 확정.** 특정 항목만 잠그는 기능은 v2 후보이고, 스키마의 `is_locked`/`enc_blob` 컬럼만 지금 비워둔다.

#### 11.3.1 실제로 밟은 지뢰 (v0.9 신설)

문서로 남기지 않으면 팀원 다섯이 같은 곳에서 각자 하루씩 태운다.

| 증상 | 원인과 처치 |
|---|---|
| Gradle `Worklets (0.12.2) is not compatible with Reanimated` | `react-native-worklets`는 **peer** 의존성이라 `pnpm.overrides`가 안 먹는다. `apps/mobile`의 **직접 의존성으로 `0.10.x`를 박는다** |
| `import { Tabs } from 'expo-router'` → `undefined is not a function` | SDK 57에서 경로가 갈렸다. **`expo-router/js-tabs`** |
| SQLite `database is locked` / `cannot rollback - no transaction is active` | 단일 연결에 동시 쓰기. **직렬 쓰기 큐**(`withWrite`)를 통과시킨다. 읽기는 WAL이라 큐에 안 태워도 된다 |
| 목 데이터가 매번 두 배로 늘어남 | StrictMode가 effect를 두 번 돈다. 모듈 레벨 프로미스 가드 **+ 트랜잭션 안에서 count 재확인** |
| 웹이 흰 화면 + `Invalid hook call` | React가 두 벌. `.npmrc`의 `node-linker=hoisted`가 옛 설치를 안 치운 것이다. `node_modules` 전부 지우고 재설치 |
| `pnpm`이 `dlx dlx dlx…` 무한 반복 | corepack이 pnpm을 다시 받는 루프. `corepack disable` + npm 전역 설치, `.npmrc`에 `manage-package-manager-versions=false` |
| Gradle이 이유 없이 죽음 | `java -version`이 17인지 먼저 본다. 그리고 **리포 경로에 한글이 있으면 안 된다** |
| 앱이 `no such column: …` | **`CREATE TABLE IF NOT EXISTS`는 이미 있는 테이블에 컬럼을 더해주지 않는다.** 새로 까는 기기는 맞고 이미 깔린 기기만 틀려서 늦게 발견된다. `PRAGMA table_info`로 보고 없으면 `ALTER TABLE ADD COLUMN`(`sqlite.ts`의 `ensureColumn`) |
| `UNIQUE constraint failed: tags.user_id, tags.name` | 삭제가 툼스톤이라(7장) **지운 태그가 이름을 계속 붙들고 있다.** 새로 만들 때는 그 행을 되살리고, 이름을 바꿀 때는 툼스톤의 이름을 비켜준다. 화면의 중복 검사는 살아 있는 것만 보므로 통과한 뒤 DB에서 터진다 |
| 목 데이터가 UNIQUE에 걸림 | 씨앗 INSERT만 `OR REPLACE`가 아니었고, "심을까" 판정이 할 일 개수만 봤다. 할 일이 지워지고 태그만 남은 상태에서 터진다 |

## 12. 화면 구성

**웹 4열** (v0.9 정정 — 3열이었다): 사이드바 / 가운데(타임라인 + 할 일 목록) / 상세 패널

- **사이드바** — 뷰 5개(오늘·다음 7일·전체·인박스·완료함, 각 진행률 %) · 태그 목록 · 하단 `⚙ 설정`. 드래그 소스. `[`로 44px 레일로 접힌다
- **가운데** — 위는 타임라인(줌 4단계 + 기간 진행률 + `고정 n/m`), 아래는 할 일 목록(검색 · `⚡ 자동 배치` · `+ 할 일`). **가로·세로 경계선을 끌어 비율을 조절**하고 localStorage에 남는다
- **상세** — 두 모드를 토글한다: **오른쪽 패널** / **리스트에서 펼치기**. 패널 모드는 바깥을 클릭하면 닫힌다
- 할 일 목록은 **막대를 끌어다 놓는 휴지통**이기도 하다 (Block만 삭제)

단축키 `N` 추가 · `1–4` 줌 · `T` 오늘 · `/` 검색 · `[` 사이드바 · `Esc` 닫기

> **CSS 주의** — 전역 클래스 한 장으로 굴러가고 있어서 같은 종류의 사고가 세 번 났다. ⑴ 후손 선택자가 너무 넓어 남의 버튼까지 잡음(`.navlist button` → `.navlist > li > button`) ⑵ 같은 특이도의 나중 규칙이 앞 규칙을 덮음 ⑶ **`z-index: 0`도 쌓임 맥락을 만들어** 그 안의 라벨이 밖으로 못 올라옴. 팀원이 붙기 전에 `@layer`나 CSS Modules로 경계를 만드는 것이 좋다.

### 14.1 M3를 M2보다 먼저 한 이유 (v0.9 변경)

원래 M2(백엔드) → M3(앱) 순서였는데 **뒤집었다.**

- **M1이 로컬 저장만으로 완결되어 있다.** 백엔드가 없어도 웹이 쓸만한지 이미 확인됐고, 같은 구조를 앱에 옮기는 데 서버가 필요 없다
- **앱에서만 드러나는 문제가 있다.** 제스처 감(롱프레스 시간, 햅틱), 좁은 화면의 정보 밀도, SQLite 동시성 — 이건 실기기에서만 판단된다. 서버를 먼저 붙였다면 이 문제들을 **동기화 버그와 뒤섞인 채로** 만났을 것이다
- **7장 동기화 계약을 서버 없이 미리 지킬 수 있다.** 앱은 지금도 `outbox` 테이블에 쓰기 로그를 쌓는다. M2에서 보내는 쪽만 붙이면 된다
- 대가: 기기 두 대에서 같은 데이터를 못 본다. **이게 지금 가장 아쉬운 지점이고 그래서 M2가 바로 다음이다**

> v0.10 시점에서 이 대가가 실제로 드러났다. 개발 중에도 맥 웹·윈도우 웹·폰이 각각 딴 데이터를 본다.
> 기능은 충분히 쌓였고, 이제 없는 것은 "두 기기에서 같은 걸 본다" 하나다.

**AI 기능을 M4.5에 둔 이유**: 이미 만들어진 코드가 있어 순수 신규 개발이 아니고, 서버 프록시(M2)가 있어야 붙일 수 있다. 다만 **M0에서 통합 방식만은 정해야** 한다 — B안이면 M3의 탭 구성이 바뀐다.

## A. 보안 상세

"암호화" 한 단어에 **서로 다른 위협을 막는 세 가지**가 섞여 있다. **실제 사고 대부분은 암호화가 아니라 권한 검사에서 난다.**

### A.1 위협 모델
| 공격자 | 노리는 것 | 현실성 | 막는 수단 |
|---|---|---|---|
| 다른 사용자 | 남의 할 일 읽기·수정 | **높음** | RLS/권한 검사 (A.4) |
| 번들 뜯는 사람 | 앱에 박힌 키로 DB·AI API 직접 호출 | **높음** | 비밀 분리 + RLS (A.5) |
| 같은 와이파이 | 트래픽 가로채기 | 중간 | TLS 1.3·HSTS (A.2) |
| 기기 주운 사람 | 저장된 토큰 | 중간 | Keystore 보관 (A.3) |
| DB 백업·디스크 유출 | 전체 데이터 | 낮음 | 저장 시 암호화 (A.2) |
| 침해된 서버 | 전체를 평문으로 | 낮음 | E2EE만이 막음 (A.2) |

위 두 줄이 실제 사고 지점. 여기부터 잡는다.

### A.2 암호화 세 층위
세 가지는 서로를 대체하지 않고 각각 다른 구간만 덮는다. TLS + 디스크 암호화를 다 켜도 **서버는 여전히 평문을 본다**.

**A. 전송 구간 (무조건)** — TLS 1.3, HTTP→HTTPS 301, HSTS.
- 인증서 핀닝은 **권하지 않음** — 갱신 시 앱이 통째로 죽는 사고가 잦다.

**B. 저장 시 암호화 (사실상 켜져 있음)** — Supabase 기본.
- 오해 주의: **디스크를 통째로 들고 나갔을 때만** 막는다. DB에 정상 접속 가능한 사람에겐 무의미하고, 대부분의 유출은 접속 권한으로 일어난다.

**C. E2EE — 확정 기능들과 정면 충돌**

| 기능 | 평문 (A+B) | E2EE |
|---|---|---|
| 검색 | tsvector | 불가 |
| 서버측 정렬 인덱스 | 인덱스+페이징 | 불가 |
| 위젯 | 로컬 DB 읽으면 끝 | 잠금해제 전 내용 못 그림 |
| 푸시 알림 | "OS 과제 마감 2시간 전" | "할 일 1건" |
| **AI 할 일 생성** (3.7) | 서버가 목표를 읽어 모델에 전달 | **불가** |
| **소셜 로그인** | 그대로 | **궁합 나쁨** — 기억하는 비밀이 없어 키 유도 불가 |
| 계정 복구 | 이메일 재설정 | **비밀번호 분실 = 영구 소실** |

구현량 +3~4주, 대부분이 암호화가 아니라 **키 관리와 복구 UX**.

**권고: v1은 A+B, E2EE 미채택.** 특정 항목만 걸리면 v2에 "잠금 항목" — `is_locked` + `enc_blob`만 지금 비워둔다.

### A.3 기기에 남는 것
| 대상 | 방법 | 주의 |
|---|---|---|
| 앱 토큰 | `expo-secure-store` (Keystore) | `AsyncStorage`는 평문, 절대 금지 |
| 앱 로컬 SQLite | 암호화 안 함 | `android:allowBackup="false"` |
| 웹 세션 | 가능하면 `httpOnly; Secure; SameSite=Lax` 쿠키 | localStorage 토큰은 XSS 한 방에 계정 넘어감 |
| 웹 로컬 캐시 | IndexedDB, 로그아웃 시 전체 삭제 | 공용 PC |

**설계 충돌: 로컬 DB를 SQLCipher로 암호화하면 위젯이 깨진다.** 키는 Keystore에 있는데 **위젯은 앱 프로세스가 아니다.**

### A.4 접근 통제 — 여기가 8할
```sql
ALTER TABLE tasks ENABLE ROW LEVEL SECURITY;
ALTER TABLE tasks FORCE ROW LEVEL SECURITY;

CREATE POLICY tasks_select ON tasks FOR SELECT
  USING (user_id = (SELECT auth.uid()));
CREATE POLICY tasks_insert ON tasks FOR INSERT
  WITH CHECK (user_id = (SELECT auth.uid()));
CREATE POLICY tasks_update ON tasks FOR UPDATE
  USING      (user_id = (SELECT auth.uid()))
  WITH CHECK (user_id = (SELECT auth.uid()));  -- ★ 빠지면 남에게 넘길 수 있다
CREATE POLICY tasks_delete ON tasks FOR DELETE
  USING (user_id = (SELECT auth.uid()));
```
자주 나는 실수:
1. **UPDATE에 `WITH CHECK` 누락** — `USING`만 있으면 내 행의 `user_id`를 남의 것으로 바꿔 밀어넣을 수 있다
2. **조인·부속 테이블에 정책 미적용** — `blocks`/`tags`/`task_tags`/**`timetables`/`routines`/`routine_checks`/`settings`**/`identities`/`devices`/`ai_generations` **전부** 건다
3. **정책만 쓰고 `ENABLE` 안 함** — RLS 켜고 정책 없으면 전부 거부(안전), 정책 쓰고 RLS 안 켜면 **전부 허용**(위험). 방향이 반대라 눈치채기 어렵다
4. `auth.uid()`를 `(SELECT auth.uid())`로 감싸지 않으면 행마다 재평가 — 느려서 정책을 끄게 되는 게 진짜 위험

**직접 짜는 경우**도 원칙 동일: 개별 쿼리에 `WHERE user_id=:me`를 붙이는 게 아니라 **레포지토리 계층에서 강제 주입**. 한 군데만 빠져도 IDOR.

### A.5 비밀 관리 — 앱에 넣은 건 전부 공개
RN 번들은 APK 뜯으면 읽힌다. "빌드 시 주입하니 안전"은 가장 흔한 착각.

| 넣어도 되는 것 | 절대 안 되는 것 |
|---|---|
| Supabase **publishable** 키, 구글 OAuth **client ID**, API base URL | Supabase **secret** 키 (**RLS 통째 우회**) / Play 서비스계정 JSON / 카카오 **Admin** 키 / DB 접속정보 / OAuth client **secret** / **생성형 AI API 키** |

**AI API 키는 특히 위험하다** — DB 유출과 달리 즉시 금전 손실이고, 남이 내 크레딧으로 아무 프롬프트나 돌린다.

publishable 키가 공개돼도 되는 유일한 이유는 **RLS가 뒤를 받치기 때문**이다.
- 서버 비밀은 EAS Secrets, 리포엔 `.env.example`만
- **`gitleaks` pre-commit 훅.** 푸시된 키는 히스토리를 지워도 샌 것 — 유일한 복구는 회전
- OAuth 리디렉트는 커스텀 스킴 대신 **Android App Links**

### A.6 입력과 출력
- **메모가 마크다운이라 XSS 표면 발생.** 렌더링 시 DOMPurify, `dangerouslySetInnerHTML` 금지. 제목·태그명·**고정 일정 이름**도 사용자 입력이다
- **AI 응답도 사용자 입력과 같이 취급**
- 웹에 **CSP 헤더**
- 서버 입력 검증은 스키마로(Zod): `estimate_min` 음수, `end_at < start_at`, `importance` 범위 밖, 거대한 `notes`, **`routines.start_min/end_min` 범위와 대소**, AI 응답 배열 길이 상한
- 동기화 배치에 **건수·바이트 상한** — 상한 없는 `POST /sync`는 그 자체로 DoS 통로

### A.8 남용 방지
